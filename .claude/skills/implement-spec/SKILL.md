# Implement Spec

## 계약

<ROLE>
승인된 스펙을 **병렬 실행 가능한 태스크로 분해하고 오케스트레이션한다.** 태스크마다 알맞은 모델·추론 레벨을 배정하고, 감독으로서 커밋과 결정을 독점하고, 현황판으로 진행을 공유하고, 합격 조건으로 마감한다.
</ROLE>

<PIPELINE>
brainstorming  →  deep-interview  →  implement-spec (이 스킬)  →  릴리스
   방향 결정         스펙 작성           병렬 구현

입력: docs/specs/{YYYY-MM-DD}-{슬러그}.md  (승인 필수)
출력: 코드 + 단계별 커밋 + HTML 현황판 + docs/decisions/{날짜}-{슬러그}-implementation.md
</PIPELINE>

<DO>
- 스펙의 **구성요소 표와 합격 조건**에서 태스크를 도출한다 — 상상으로 만들지 않는다
- 태스크마다 소유 디렉터리를 배타적으로 배정한다
- 실행 전에 분해·배정표를 사용자에게 보여주고 승인받는다
- HTML 현황판을 실행 전에 띄우고 진행마다 갱신한다
- 에이전트에게 커밋을 금지하고 감독이 단계별로 커밋한다
- 스펙의 "남은 위험" 항목을 해당 태스크 프롬프트에 경고로 박는다
- 각 태스크가 자기 합격 조건을 검증하게 하고, 검증 결과를 보고받는다
</DO>

<DO-NOT>
- 승인 안 된 스펙으로 시작하지 않는다 → 승인부터 받는다
- 스펙에 없는 결정을 에이전트가 임의로 내리게 두지 않는다 → 결정 요청으로 올린다
- 에이전트끼리 같은 파일을 만지게 두지 않는다
- Workflow 실행 중에 사용자에게 물으려 하지 않는다 — **불가능하다**. 결정은 수거 후 처리한다
- 합격 조건을 안 채운 채 완료 보고하지 않는다
</DO-NOT>

<LANGUAGE>
진행과 산출물은 항상 한국어. 코드·명령·에러 문자열은 원문 유지.
</LANGUAGE>

## 이 스킬이 존재하는 이유

스펙까지 나왔는데 구현이 한 세션에서 순차로 돌면, 컨텍스트가 먼저 죽는다. 실측: 패키지 3개짜리 작은 릴리스 하나에 에이전트들이 합계 76만 토큰을 썼다. 같은 일을 인라인으로 했으면 절반도 못 가서 컨텍스트가 찼다.

그래서 이 스킬은 세 가지를 한다.

1. **분해와 배정.** 스펙의 구성요소를 의존 그래프로 세우고, 병렬 가능한 것을 골라내고, 난도에 맞는 모델·추론 레벨을 붙인다. OKLCH 대비 계산과 워크플로 YAML 한 장은 같은 값을 쓸 이유가 없다.
2. **감독 권한 집중.** 커밋·판정·현황 보고를 감독이 독점한다. 에이전트가 각자 커밋하면 git index가 경합하고, 각자 결정하면 스펙에 없는 선택이 소리 없이 코드에 박힌다.
3. **합격 조건으로 마감.** 스펙이 이미 검증 가능한 조건을 갖고 있다. 그걸 태스크에 나눠 붙이고 대조표로 닫는다.

## 쓰지 않아야 할 때

- 승인된 스펙이 없다 → `brainstorming` 또는 `deep-interview`부터
- 파일 하나 고치면 끝난다 → 그냥 고친다
- 태스크가 2개 이하이고 전부 순차 의존이다 → 인라인이 더 빠르다
- 사용자가 직접 개입하며 방향을 틀고 싶어한다 → 서브에이전트는 실행 중 개입이 안 된다. 인라인으로 하거나 별도 세션을 열게 한다

## 절대 규칙

**Workflow 실행 중에는 사용자에게 물을 수 없다.** 스크립트는 백그라운드에서 결정적으로 흐른다. 그래서 애매한 결정은 (a) 실행 전 승인 관문에서 미리 정하거나, (b) 에이전트가 `decisionRequests`로 올려 실행 후 처리하거나, (c) 진짜 차단이면 그 태스크만 멈추고 나머지를 끝낸 뒤 감독이 사용자에게 묻는다. 셋 중 하나다.

**에이전트는 커밋하지 않는다.** 병렬 에이전트가 동시에 `git add`하면 index가 깨진다. 감독이 태스크 완료마다 커밋한다.

**소유 디렉터리는 배타적이다.** 두 태스크가 같은 디렉터리를 쓰면 병렬로 돌리지 않는다. 순차로 바꾸거나 경계를 다시 긋는다.

**실행 전 승인 없이 Workflow를 부르지 않는다.** 에이전트 N개가 동시에 파일을 쓰는 일이다. 분해가 틀리면 되돌리는 비용이 실행 비용보다 크다.

## 1단계 — 스펙 적재

1. `docs/specs/`에서 대상 스펙을 찾는다. 인자로 경로가 오면 그것, 없으면 가장 최근 것을 제안하고 확인받는다
2. 메타의 **승인** 항목을 확인한다. `대기 중`이면 멈추고 승인을 받는다
3. 다음을 추출한다:
   - **구성요소 표** — `진행` 항목만. `보류`는 태스크로 만들지 않는다
   - **합격 조건** — 태스크에 나눠 붙일 검증 게이트
   - **제약 / 하지 않을 것** — 에이전트 프롬프트에 그대로 넣을 금지 사항
   - **남은 위험** — 해당 태스크에 경고로 박는다. 이 항목은 실제로 터진다
   - **근거 링크**(`docs/decisions/`) — 이미 판정된 것을 다시 논의하지 않기 위해
4. 저장소 현재 상태를 확인한다 — 이미 구현된 부분이 있으면 태스크에서 뺀다

## 2단계 — 분해와 배정

### 태스크 도출

구성요소 하나가 태스크 하나가 되는 경우가 많지만 기준은 **소유 디렉터리**다. 같은 디렉터리를 쓰는 구성요소는 한 태스크로 묶는다.

각 태스크에 정의할 것:

| 항목 | 내용 |
|------|------|
| 소유 범위 | 배타적 디렉터리. 다른 태스크와 겹치면 안 됨 |
| 의존 | 선행 태스크 (없으면 첫 웨이브) |
| 합격 조건 | 이 태스크가 검증할 조건 (스펙에서 발췌) |
| 모델·추론 | 아래 기준 |
| 위험 경고 | 스펙 "남은 위험" 중 해당 항목 |

### 모델·추론 레벨 기준

| 성격 | 모델 | 추론 | 예 |
|------|------|------|-----|
| 수학·알고리즘·되돌리기 비싼 설계 | opus | high~xhigh | 색공간 변환, 스키마 설계, 마이그레이션 |
| 일반 구현 (기존 패턴 따라가기) | sonnet | 기본 | 컴포넌트, API 핸들러, 설정 앱 |
| 기계적 단일 파일 | haiku | low | CI 워크플로, 설정 파일, 상수 추가 |
| 검증·리뷰 | sonnet~opus | high | 통합 검증, 교차 확인 |

확신이 없으면 한 단계 올린다. 재작업 비용이 추론 비용보다 크다.

### 병렬 판정

- **의존 없음 + 소유 디렉터리 안 겹침** → 병렬
- 후속 태스크가 선행의 *산출물*이 아니라 *이름 규약*만 필요하다면 → **병렬 가능**. 규약은 스펙에 있다
- 진짜 배리어(전원 결과를 모아야 다음이 성립)만 배리어로 둔다

### 승인 관문

분해표를 보여주고 `AskUserQuestion`으로 승인받는다. 선택지는 `이대로 실행` / `배정 조정` / `태스크 분해 수정` / `여기서 멈춤`.

```
## 분해 결과 — {스펙 제목}

| # | 태스크 | 소유 범위 | 의존 | 모델·추론 | 합격 조건 |
|---|--------|-----------|------|-----------|-----------|
| 1 | ... | packages/x | — | opus·high | 조건 2건 |

웨이브 1(병렬): 1, 2, 3
웨이브 2: 4 (1·2 의존)
감독 처리: 커밋, 결정 판정, 합격 조건 대조
```

## 3단계 — 현황판 개설

Workflow를 부르기 **전에** HTML 현황판을 만들어 Artifact로 배포하고 URL을 사용자에게 준다. 실행 중에는 감독이 개입할 수 없으므로, 사용자가 무엇이 돌고 있는지 볼 수 있는 창구는 이것과 `/workflows`뿐이다.

절 구성 4개:

| 절 | 내용 |
|----|------|
| 요약 | 완료 단계 / 합격 조건 진척 / 대기 중 결정 / 커밋 수 |
| 태스크 | 태스크별 소유 범위·상태(대기·진행·완료) 한 줄씩 |
| 결정 기록 | 감독이 내린 판정과 근거. 실행 후 채워진다 |
| 로그 | 시각 + 사건. 최신이 아래 |

`artifact-design` 스킬을 로드해 페이지를 만든다. 파일은 스크래치패드에 두고, 갱신할 때마다 **같은 경로로 재배포해 URL을 유지**한다. favicon도 고정한다.

갱신 시점: 개설 → Workflow 완료 수거 → 결정 판정 후 → 마감.

## 4단계 — Workflow 실행

승인 후 Workflow 스크립트를 만든다. 뼈대:

```js
export const meta = {
  name: 'implement-{슬러그}',
  description: '{스펙 제목} 구현',
  phases: [{ title: '구현' }, { title: '검증' }],
}

const REPORT = {
  type: 'object',
  properties: {
    files: { type: 'array', items: { type: 'string' } },
    verification: { type: 'string' },        // 합격 조건 검증 결과
    ownDecisions: { type: 'array', items: { type: 'string' } },  // 스펙이 위임해 직접 정한 값
    decisionRequests: { type: 'array', items: { type: 'string' } }, // 감독 판정 필요
    blocked: { type: 'boolean' },
  },
  required: ['files', 'verification', 'decisionRequests', 'blocked'],
}

const TASKS = [ /* 2단계 분해 결과 */ ]

phase('구현')
const results = await parallel(TASKS.map(t => () =>
  agent(buildPrompt(t), { label: t.name, model: t.model, effort: t.effort, schema: REPORT })))

return { results: results.filter(Boolean) }
```

### 에이전트 프롬프트 템플릿

각 태스크 프롬프트에 반드시 넣을 것:

```
{작업 설명}. 저장소: {경로}

## 필독
- {스펙 경로} — 최우선 진실
- {결정 기록 경로} — 이미 판정된 것
- {참고 패턴 경로} (read-only)

## 소유 범위
`{디렉터리}` 안의 파일만 만들고 수정한다. 다른 곳은 건드리지 않는다.

## 병렬 전제
{다른 태스크}가 동시에 진행 중이다. 그쪽 파일을 건드리지 마라.
완성을 기다리지 마라 — {필요한 규약}은 스펙에 고정돼 있다.

## 위험 경고
{스펙 "남은 위험" 중 해당 항목} — 실제로 터질 수 있다.

## 검증
{합격 조건}을 직접 수행하고 결과를 보고하라.

## 규칙
- git commit 금지 (감독이 커밋)
- pnpm/npm install 시 lockfile 경합 에러가 나면 5~10초 대기 후 재시도 (최대 3회)
- 스펙이 위임한 값은 직접 정하고 `ownDecisions`에 남겨라
- 스펙과 충돌하거나 스스로 못 정할 결정은 `decisionRequests`에 올리고 그 부분만 멈춰라
```

### 규모

세션의 workflow size 가이드라인을 따른다. 초과할 것 같으면 웨이브를 나눠 여러 번 실행한다.

## 5단계 — 수거와 판정

Workflow가 끝나면:

1. **결정 요청 처리** — `decisionRequests`를 모아 판정한다. 스펙·결정 기록에서 근거를 찾을 수 있으면 감독이 판정하고, 스펙 범위를 벗어나면 사용자에게 묻는다. 판정 결과는 현황판 「결정 기록」에 근거와 함께 남긴다
2. **교차 검증** — 태스크 경계에서 실제로 맞물리는지 확인한다 (예: A가 참조하는 이름이 B에 정의됐는지). 에이전트는 자기 범위만 봤다
3. **커밋** — 태스크 단위로 나눠 커밋한다
4. **재실행이 필요하면** `resumeFromRunId`로 이어간다 — 바뀌지 않은 앞부분은 캐시에서 즉시 돌아오고 수정한 지점부터 다시 실행된다

## 6단계 — 마감

1. **합격 조건 대조표** — 조건별 통과/미통과와 근거를 보여준다. 미통과가 있으면 완료라고 하지 않는다
2. **구현 결정 기록** — `docs/decisions/{날짜}-{슬러그}-implementation.md`에 남긴다. 스펙이 위임해 구현 중 정해진 값(`ownDecisions`), 감독 판정, 실제로 터진 위험과 해법. 3개월 뒤 "왜 이 값이지"에 답하는 문서다
3. **스펙 스탬프** — 스펙 메타에 구현 완료를 표시하고, 완료된 스펙은 `docs/specs/archive/`로 옮긴다
4. **현황판 최종 갱신** — 전 태스크 완료, 합격 조건 진척, 결정 기록 전량 반영 후 재배포
5. **현황 보고** — 태스크별 결과, 커밋 목록, 남은 것

## 예시

<good>
분해가 소유 디렉터리 기준:
```
1. tokens (packages/tokens)   — opus·high  — 대비 검사 게이트
2. Button (packages/react)    — sonnet     — 토큰 이름은 스펙 고정 → 1과 병렬
3. CI (.github)               — haiku·low  — 독립
```
좋은 이유: 셋이 서로 다른 디렉터리를 갖고, 2가 1의 산출물이 아니라 이름 규약만 필요해서 병렬이 성립한다.
</good>

<bad>
```
1. 토큰 정의 (packages/tokens/src/tokens.ts)
```
