# Brainstorming — 개발 전 토론

## 계약

<ROLE>
기능을 만들기 전에 "어떻게 만들면 좋을지"를 사용자와 토론해 **방향을 정한다.** 선택지를 펼치고, 트레이드오프를 비교하고, 하나에 합의하는 것까지가 이 스킬의 일이다.
</ROLE>

<PIPELINE>
brainstorming (이 스킬)  →  deep-interview  →  구현
     방향 결정                세부 구체화        코드

brainstorming 산출물: docs/decisions/{YYYY-MM-DD}-{슬러그}.md  (왜 이렇게 정했나)
deep-interview 산출물: docs/specs/{YYYY-MM-DD}-{슬러그}.md      (정확히 무엇을 만드나)
                                          ^^^^^^^ 두 파일은 같은 슬러그로 짝을 이룬다
</PIPELINE>

<DO>
- 선택지를 2~3개로 펼치고 트레이드오프와 추천안을 함께 제시한다
- 한 번에 하나씩 질문한다
- 요청 규모를 spike / bounded / architectural로 분류하고 소리 내어 밝힌다
- architectural이면 결정 기록(`docs/decisions/`)을 쓴다
- 매 경로 끝에서 사용자 승인을 받는다
</DO>

<DO-NOT>
- 스펙 파일(`docs/specs/`)을 쓰지 않는다 — deep-interview의 몫이다
- 모호도 점수를 매기지 않는다 — deep-interview의 장치다
- 합격 조건·상세 제약을 결정 기록에 쓰지 않는다 — 스펙의 몫이다
- 승인 전에 코드를 쓰거나 파일을 만들지 않는다(결정 기록은 예외)
- 확정용 세부 질문("정확히 어떤 값인가", "완료 조건은")으로 파고들지 않는다 — 그 질문이 필요해지면 토론이 끝난 신호다
</DO-NOT>

<HANDOFF>
IF 토론에서 아래 중 하나라도 안 나왔다 → deep-interview로 넘긴다
  - 실패했을 때의 동작
  - "됐다"를 확인하는 방법
  - 경계값(빈 값, 대량, 동시 실행)
  - 기존 데이터·하위 호환
ELSE → 바로 구현해도 된다

인계할 때 전달할 것: 슬러그, 결정 기록 경로, "안 정해진 것" 목록
</HANDOFF>

<ASK>
질문은 `AskUserQuestion` 도구로 던진다. 채팅에 평문으로 나열하지 않는다 — 사용자가 답을 흘리거나 일부만 답한다.

호출당 결정 하나. 선택지 2~4개. 각 선택지의 description에 트레이드오프를 한 줄로 적는다. 추천안은 맨 앞에 놓고 label 끝에 `(Recommended)`를 붙인다. "기타" 선택지는 만들지 않는다 — 자유 입력이 자동으로 붙는다.

평문으로 물어도 되는 경우: 선택지가 아직 없는 열린 탐색("이걸 왜 만들고 싶어?"), spike의 동의 확인.
</ASK>

<LANGUAGE>
대화와 산출물은 항상 한국어. 사용자가 영어로 말해도 마찬가지다.
</LANGUAGE>

**중복 방지 규칙:** 탈락한 선택지와 그 이유는 결정 기록에만. 합격 조건과 상세 제약은 스펙에만. 스펙은 결정 기록을 링크로 가리킬 뿐 내용을 복사하지 않는다.

<HARD-GATE>
무엇을 하려는지 사용자에게 말하고 승인받기 전에는, 코드를 쓰거나 프로젝트를 스캐폴딩하거나 어떤 구현 행동도 하지 않는다. 아래 모든 경로의 모든 작업에 적용된다 — 절차의 무게는 작업 크기에 따라 달라지지만, 승인 게이트는 절대 달라지지 않는다.
</HARD-GATE>

## 세 갈래

첫 질문을 던지기 전에 요청을 분류하고, **분류 결과를 소리 내어 말한다** — "이건 bounded로 보여서 스펙 파일 대신 짧은 설계를 여기서 제시할게" — 사용자가 뒤집을 수 있게.

**Spike** — 타당성 질문("이거 가능해?", "되나 확인만", "대충 해도 됨"). 산출물은 답이지 남길 코드가 아니다.
→ 질문과 시도할 방법을 2~3문장으로 제시, 동의받고, 정확성이 허락하는 선에서 가장 싸게 확인. 설계 문서도 스펙 파일도 없음. 결과는 권고안으로 보고하고, 만든 것은 전부 "버릴 것"이라고 명시.

**Bounded** — 이미 이 저장소에 존재하는 코드에 대한 잘 정의된 변경: 플래그 추가, 작은 엔드포인트, 한 파일 수정.
→ 어떤 종류의 앱인지 아는 것만으로는 부족하다. bounded는 **바꾸려는 흐름이 이미 여기 읽을 수 있는 형태로 존재한다**는 뜻이다. 바꿀 기존 흐름이 없으면 bounded가 아니다. 중요한 질문만 하고, **채팅으로 짧은 설계**(몇 문장~몇 단락)를 제시하고, **멈춘다**. 승인이 나온 뒤에만 구현 시작 — bounded의 승인 게이트도 architectural만큼 단단하다. 스펙 파일도 구현 계획 문서도 없음.

**Architectural** — 새 프로젝트, 새 서브시스템, 컴포넌트 간 관계를 재구성하거나 다른 곳이 의존하는 인터페이스를 바꾸는 변경.
→ 전체 절차: 질문 → 접근법 2~3개 비교 → 섹션별 설계 제시 → 방향 합의. 여기까지가 이 스킬의 몫이고, 스펙 문서는 deep-interview가 이어받는다.

두 갈래 사이에서 애매하면 **더 무거운 쪽**을 택한다. 래칫은 한 방향이다 — 작업 중간에 숨은 복잡도가 드러나면 경로를 올린다. 멈추고, 그렇다고 말하고, 올린다. **작업 중간에 내려가는 일은 없다.**

## 안티패턴: "이건 너무 간단해서 승인 필요 없음"

모든 경로는 구현 전 사용자 승인으로 끝난다. 할 일 목록 하나, 함수 하나짜리 유틸, 설정 값 변경 — 설계가 채팅 두 문장일 수는 있어도, 제시하고 승인받는 것은 반드시 해야 한다. "간단한" 작업이야말로 검증 안 된 가정 때문에 헛일이 가장 많이 생기는 곳이다. 작업이 간단해지면 **산출물**이 작아지는 것이지, 승인이 사라지는 게 아니다.

## 레드 플래그

| 이런 생각이 들면 | 실제로는 |
|---|---|
| "이건 너무 간단해서 설계가 필요 없어" | 간단하다는 건 설계가 짧다는 뜻이지 없다는 뜻이 아니다. 채팅 두 문장, 그리고 승인. |
| "bounded라고 부르고 스펙을 건너뛰자" | 건너뛸 명분을 찾고 있다는 것 자체가 의심의 증거다. 더 무거운 쪽으로. |
| "bounded고 설계가 뻔하니까 읽는 동안 시작해야지" | 게이트는 설계의 길이가 아니라 승인이다. 제시하고, 예스를 들을 때까지 멈춘다. |
| "이런 종류의 앱은 잘 아니까 bounded야" | bounded는 내 익숙함이 아니라 저장소를 재는 말이다. 새 프로젝트엔 기존 흐름이 없으니 architectural이다. |
| "spike가 잘 돌아가니 코드를 남기자" | spike의 산출물은 답이다. 코드를 남기는 건 새 요청이니 다시 분류한다. |
| "커졌지만 거의 다 됐으니 재분류는 생략" | 숨은 복잡도는 경로를 올린다. 멈추고 말한다. |
| "spike를 승인했으니 후속 변경도 승인된 것" | 작업마다 각자의 분류와 각자의 승인을 받는다. |

## 체크리스트

먼저 분류하고, 경로를 밝히고, 해당 경로의 항목을 순서대로 완료한다.

**Spike**
1. 프로젝트 맥락 파악 — 탐색을 구성할 만큼만
2. 질문 + 탐색 계획 제시 — 2~3문장
3. 승인 — 끄덕임이면 충분
4. 조사 — 정확성이 허락하는 선에서 가장 싸게
5. 결과 보고 — 권고안 형태, 만든 것은 "버릴 것"으로 명시

**Bounded**
1. 프로젝트 맥락 파악 — 파일, 문서, 최근 커밋 확인
2. 확인 질문 — **한 번에 하나씩**, 중요한 것만
3. 채팅으로 짧은 설계 제시 — 접근법, 건드릴 파일, 검증 방법
4. 승인 — `AskUserQuestion`으로 묻고 **멈춘다.** 설계를 제시하면서 같은 호흡에 시작하는 것은 게이트를 건너뛰는 것이다
5. 다음 단계 선택 — 바로 구현할지, deep-interview로 세부를 채울지 묻는다(아래 참조)

**Architectural**
1. 프로젝트 맥락 파악 — 파일, 문서, 최근 커밋 확인
2. 확인 질문 — 한 번에 하나씩. 목적·제약·성공 기준을 이해할 때까지
3. 접근법 2~3개 제안 — 트레이드오프와 추천안 함께
4. 설계 제시 — 복잡도에 맞춰 섹션을 나누고, **각 섹션마다** 맞는지 확인받기
5. 방향 합의 — 정해진 것과 아직 안 정해진 것을 한 번에 정리해 확인받는다
6. deep-interview로 인계 — 합의된 방향을 넘기며 스펙 작성으로 넘어갈지 묻는다

**터미널 상태는 경로에 묶여 있다.** Spike는 권고안 보고에서 끝난다(구체화할 게 없다 — 답이 산출물이다). Bounded는 승인 후 구현 또는 deep-interview. Architectural은 방향 합의 + 결정 기록에서 끝나고, 스펙 문서는 deep-interview가 쓴다. 어느 경로에서도 승인 없이 다음 단계로 넘어가지 않는다.

승인이 안 나면 되돌아간다: 설계를 고쳐 다시 제시한다.

### deep-interview로 넘길지 판단

토론이 정하는 건 **방향**이고, deep-interview가 챙기는 건 **토론에서 안 나온 것**이다. 아래 중 하나라도 걸리면 넘기는 쪽이 맞다:

- 실패했을 때 어떻게 되는지 대화에서 한 번도 안 나왔다
- "됐다"를 무엇으로 확인할지 못 정했다
- 경계값(빈 값, 아주 많음, 동시 실행)을 안 건드렸다
- 기존 데이터·하위 호환이 걸려 있다
- 나중에 "왜 이렇게 했지"를 되짚을 것 같다

전부 아니면 바로 구현해도 된다. 파일 하나 고치는 작업까지 스펙을 쓰는 건 절차를 위한 절차다.

## 프로세스

아래는 bounded와 architectural 경로용이다(spike는 "탐색 계획 제시하고 동의받기"에서 멈춘다). **접근법 탐색** 이후 절은 architectural 깊이다 — bounded는 맥락 + 질문 몇 개 + 짧은 채팅 설계가 전부다.

여기서 던지는 질문은 **방향을 고르는 질문**이다. "정확히 어떤 값인가", "완료 조건은 뭔가" 같은 확정용 질문이 필요해지는 순간이 오면, 그건 토론이 끝났다는 신호다 — 계속 파지 말고 방향 합의로 마무리하고 deep-interview로 넘긴다.

**아이디어 이해하기**
- 현재 프로젝트 상태부터 확인한다(파일, 문서, 최근 커밋)
- 세부 질문 전에 규모를 먼저 잰다. 요청이 독립된 서브시스템 여러 개를 담고 있으면(예: "채팅 + 파일 저장 + 결제 + 분석이 있는 플랫폼") 즉시 지적한다. 쪼개야 할 프로젝트의 세부를 다듬는 데 질문을 쓰지 않는다
- 스펙 하나로 담기엔 큰 프로젝트면 분해를 돕는다: 독립된 조각이 뭔지, 서로 어떻게 연결되는지, 어떤 순서로 만들지. 그다음 첫 조각만 정상 흐름으로 브레인스토밍한다. 각 조각은 자기만의 스펙 → 계획 → 구현 사이클을 갖는다
- 규모가 적절하면 질문을 하나씩 던져 아이디어를 다듬는다
- **선택지를 댈 수 있으면 `AskUserQuestion`으로 던진다.** 사용자가 고를 법한 실제 갈래를 넣는다 — 빈칸을 채우려고 억지 선택지를 만들지 않는다
- 아직 선택지가 없는 열린 탐색이면 평문으로 묻는다. 토론 초반에는 이쪽이 정상이다
- **메시지당 결정 하나.** 한 주제에 탐색이 더 필요하면 여러 질문으로 나눈다
- 목적·제약·성공 기준을 이해하는 데 집중한다

**접근법 탐색**
- 서로 다른 접근법 2~3개를 트레이드오프와 함께 제안한다
- **`AskUserQuestion`으로 던진다.** 각 접근법이 선택지 하나, description에 트레이드오프 한 줄
- 추천안을 맨 앞에 놓고 label 끝에 `(Recommended)`를 붙인다. 왜 추천하는지는 도구 호출 직전 본문에 한두 문장으로 밝힌다
- **YAGNI를 가차 없이 적용한다** — 모든 접근법과 설계에서 불필요한 기능을 걷어낸다

**설계 제시**
- 무엇을 만드는지 이해했다는 확신이 서면 설계를 제시한다
- 각 섹션을 복잡도에 맞게 조절한다: 단순하면 몇 문장, 미묘하면 200~300단어까지
- 섹션마다 여기까지 맞는지 `AskUserQuestion`으로 확인한다 — `이대로 진행` / `이 부분 수정` / `다시 논의` 정도면 충분하다
- 다룰 것: 아키텍처, 구성요소, 데이터 흐름, 에러 처리, 검증 방법
- 말이 안 되는 부분이 있으면 되돌아가 다시 확인할 준비를 한다
- 목업·와이어프레임·다이어그램처럼 **글보다 그림이 명백히 나은 질문**에서만 `show_widget`으로 시각화한다. UI가 주제라고 해서 시각적 질문인 건 아니다 — "이 맥락에서 '가벼움'이 뭘 뜻하나요?"는 개념 질문이라 글로, "어느 레이아웃이 나은가요?"는 시각 질문이라 그림으로

**격리와 명료함을 위한 설계**
- 시스템을 각각 하나의 분명한 목적을 갖고, 잘 정의된 인터페이스로 소통하고, 독립적으로 이해·검증 가능한 작은 단위로 나눈다
- 각 단위마다 답할 수 있어야 한다: 무엇을 하는가, 어떻게 쓰는가, 무엇에 의존하는가
- 내부를 읽지 않고도 무엇을 하는지 알 수 있는가? 소비자를 깨뜨리지 않고 내부를 바꿀 수 있는가? 아니라면 경계 설정이 덜 됐다
- 작고 경계가 분명한 단위는 나중에 다루기도 쉽다. 파일이 커진다는 건 대개 너무 많은 일을 하고 있다는 신호다

**기존 코드베이스에서 작업할 때**
- 변경을 제안하기 전에 현재 구조를 탐색한다. 기존 패턴을 따른다
- 기존 코드의 문제가 이번 작업에 영향을 준다면(너무 커진 파일, 불분명한 경계, 엉킨 책임) 표적 개선을 설계에 포함한다 — 자기가 손대는 코드를 개선하는 좋은 개발자처럼
- 무관한 리팩터링은 제안하지 않는다. 지금 목표에 봉사하는 것에만 집중한다

## 방향 합의 이후 (architectural 경로)

토론이 끝나면 **결정 기록**을 쓴다. `date +%F`로 날짜를 얻어 `docs/decisions/{YYYY-MM-DD}-{슬러그}.md`에 저장한다. 슬러그는 주제를 알아볼 수 있는 짧은 영문 kebab-case — **deep-interview가 같은 슬러그로 스펙을 쓰므로 짝이 맞아야 한다.**

```markdown
# {제목}

- 날짜: {YYYY-MM-DD}
- 경로: architectural
- 상태: 결정됨 | 재검토 필요
- 스펙: docs/specs/{같은-슬러그}.md (deep-interview 진행 후 채움)

## 배경
{왜 지금 이 결정을 하게 됐는지 2~3문장}

## 검토한 선택지
| 선택지 | 장점 | 단점 | 판정 |
|--------|------|------|------|
| {A} | | | **채택** |
| {B} | | | 탈락 — {이유} |

## 결정
{무엇을 택했는지, 결정적 이유 한두 문장}

## 정해진 것
- {결정}: {이유 한 줄}

## 안 정해진 것
- {미결}: {지금 안 정해도 되는 이유, 또는 스펙 단계에서 물을 것}

## 뒤집을 조건
{이 결정을 재검토해야 하는 신호. 없으면 "없음"}
```

**탈락한 선택지와 그 이유가 이 문서의 존재 이유다.** 3개월 뒤 "왜 B로 안 했지"에 답하는 건 이 표다. 반대로 합격 조건·상세 제약은 여기 쓰지 않는다 — 스펙의 몫이다.

문서를 쓴 뒤 `AskUserQuestion`으로 다음 단계를 묻는다. 선택지는 이렇게 구성한다:

- `deep-interview로 구체화` — 안 정해진 것을 스펙으로 굳힌다. 위 HANDOFF 조건에 걸리면 이쪽이 추천
- `바로 구현` — 방향만으로 충분한 규모일 때
- `여기서 멈춤` — 결정 기록만 남기고 나중에 이어서

인계를 택하면 슬러그와 "안 정해진 것" 목록을 전달하며 deep-interview를 호출한다. bounded·spike 경로는 문서를 쓰지 않는다 — 채팅 설계로 끝난다.
