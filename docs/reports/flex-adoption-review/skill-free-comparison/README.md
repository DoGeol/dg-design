# 디자인 스킬·포니테일을 제외한 재검토

2026-10-08 · 비교 대상 A: `ea9c55b`의 [기존 적용안](../design-application/README.md) · B: 이번 원문 우선 재검토.

이번 B안에는 디자인 스킬과 포니테일 지침을 적용하지 않았다. 저장된 fx/fxm 원문과 원본 이미지, 실제 DDS 코드·프로젝트 계약을 근거로 삼았다. A에도 원문 분석과 프로젝트 제약이 섞여 있으므로 **아래 차이를 스킬 하나의 인과 효과라고 단정할 수 없다.** 동일 과제를 별도 근거로 재검토한 두 설계안의 비교다.

## 결론

외형의 가장 큰 차이는 radius 몇 px보다 **컨트롤이 화면 안에서 조합되는 방식**이다. A는 현재 DDS 크기·형태를 출발점으로 토큰을 연결하고 필요한 조합을 단계적으로 추가했다. B는 flex에서 핵심으로 다룬 List·선택 트리거·작업 모달·모바일 사전 조합을 먼저 표준 사용례로 정의한 다음 DDS에 대응시킨다.

A도 List·PropertyField·Dialog 부품·box/line을 제안했다. B가 이를 처음 발견한 것은 아니다. **선택적 후속 확장이던 항목을 설계의 중심에 두는 것**, 원문 근거가 약한 새 숫자를 고정하지 않는 것이 주된 차이다.

- [시각 비교판](comparison.html): 두 안의 대표 선택을 같은 콘텐츠·브랜드로 비교한다. 모바일/데스크톱, 주제 전환을 지원한다.
- [컴포넌트 38개 비교](components.md): 달라지는 부분과 결론이 유지되는 부분.
- [폼 비교 캡처](comparison-form.png): 비교판을 브라우저에서 확인한 이미지.

비교판은 두 문서안의 설명용 재구성이다. 현 DDS의 실제 렌더, 모든 최종 variant, 스킬 유무에 대한 성능 실험을 보여주는 것이 아니다. 패키지 코드를 import하거나 변경하지 않는다.

## 적용 결과의 차이

| 주제 | A: 앞선 적용안 | B: 스킬 없이 원문에서 재검토 | 눈에 보이는 결과 |
| --- | --- | --- | --- |
| 전체 구성 | 38개 부품의 토큰·CSS부터 정렬 | 객체 목록·폼·작업 패널 사용례부터 정렬 | 독립 컨트롤보다 실제 작업 화면의 일관성이 먼저 드러남 |
| Select | field 모양 기본, 트리거 합성 확장 | Field/Button/Chip 트리거를 동등한 표준 사용례로 설계 | 제목 옆·툴바·속성 행에서도 같은 선택기가 등장 |
| List | 실사용 두 곳 검증 후 신규 후보 | leading/main/trailing 조합과 그룹 헤더를 우선 설계 | 사람·문서·버전이 각 정보량에 맞는 행을 공유 |
| TextField/PropertyField | 외부 label 기본, 내부 label·box/line 후보 | 묶인 폼은 box, 단독·분절 입력은 line, 비키보드 값은 property | 모든 값이 테두리 있는 input 형태로 보이지 않음 |
| Radio/설정 | 기존 브랜드 선택 표시 유지 | 중성 선택 표시와 약한 행 표면을 별도 설정 조합으로 검토 | 선택은 조용하게, 저장 CTA는 더 명확하게 보임 |
| DropdownMenu | 기본 메뉴 치수와 Sub 확장 우선 | 상하 보조 영역·그룹·설정 항목까지 사용례로 설계 | 설명·명령·설정이 계층적으로 조합됨 |
| Dialog | 기본 확인형 유지, 작업형 부품 확장 | 중앙/측면/전체 보기와 Toolbar/Aside/본문 Footer를 함께 설계 | 같은 작업을 다른 보기로 계속 진행 가능 |
| 모바일 Sheet | 높이·safe area·스크롤 정리 | 같은 컨테이너에서 간단→상세→전체 보기 전환까지 정의 | 단계가 깊어져도 이전 입력 맥락이 이어짐 |
| spacing/radius | r14/p8, r12/p6 같은 조합 후보 제시 | 원문에서 확인한 상대 관계만 근거로 두고 실제 화면별 검수 | 같은 반경 공식을 모든 패널에 강제하지 않음 |
| 피드백 소형 부품 | 대부분 기존 DDS 유지 | 대부분 같은 결론 | Spinner·Progress·Toast 등에 차이를 억지로 만들지 않음 |

## 원문을 다시 읽으며 수정한 판단

**데스크톱의 자유도와 모바일의 제약은 다르다.** fx는 다양한 트리거·슬롯 합성을 지향한다. fxm은 액세서리와 형태 조합을 미리 정하고 일부 외형 커스텀을 제한한다. B에서는 공통 foundation 위에 desktop의 조합 API와 mobile의 허용 조합을 따로 문서화한다. 새로운 패키지로 전부 나누겠다는 뜻은 아니다.

**브랜드 색이 모든 선택 상태를 맡을 필요는 없다.** DS026은 중성 radio, 약한 행 배경, 강한 저장 CTA를 함께 보여준다. B는 이 설정 조합을 비교 대상으로 올린다. 단일 이미지가 모든 Radio의 공식 색 규칙을 입증하지는 않으므로 기존 브랜드형도 유효하다. 사용자 브랜드 블루 자체는 유지한다.

**도메인 표식과 조작 아이콘을 구분한다.** DS018은 값 이해를 돕는 코드 배지와 이모지 등을 사용한다. 같은 아이콘 세트 규칙은 시스템 조작 아이콘에 적용하고, 도메인 데이터의 의미를 설명하는 아바타·이미지·표식은 슬롯으로 허용할 수 있다. 장식 목적으로 아무 이모지나 추가하는 결론은 아니다.

**수치가 덜 확정될 수도 있다.** 스킬을 빼면 더 큰 반경·더 많은 여백이 자동으로 답이 되지 않는다. 인접/그룹 간격을 무조건 1:2로 만들거나 바깥 반경을 항상 안쪽 반경+padding으로 확정할 원문 근거는 없다. 이미지 일부에서 관찰한 관계는 유지하되 조형 검수의 출발점으로 쓴다. 앞선 40/56, 6/16 등의 재구성 값은 계속 후보이지 공식 토큰이 아니다.

**원문에 없는 정교함은 추가하지 않는다.** 별도 근거 없이 press scale, spring, blur 전환, 새로운 shadow 단계, 500/600 weight를 넣지 않는다. 이것은 포니테일 적용 결과가 아니라 근거 범위를 구분한 판단이다.

## 스킬을 제외해도 유지되는 것

브랜드 블루·semantic token·기존 API 호환·named export·다크 패널 1px 경계·포커스와 선택 구분·label/error 연결·가상화 계산·날짜 값 모델은 DDS와 사용자 요구에서 나온 계약이다. 이를 바꾸는 것이 “스킬 미사용”을 의미하지 않는다.

또한 원문의 P3 램프 전체나 폰트·모션·정확한 CSS px를 복원했다고 말할 수 없다. 글은 과거 작업과 탐색안을 포함하며 fxm의 일부 동작은 Origami 프로토타입이다. B도 새 헤드리스 시스템·제스처·HR 기능을 자동 구현 범위로 넣지 않는다.

## 권장 적용 순서의 변화

| 단계 | A | B |
| --- | --- | --- |
| 1 | 기존 값에 역할 토큰 연결 | List/선택/작업 모달의 대표 과업과 desktop/mobile 허용 조합 정의 |
| 2 | 폼 크기·표면·반경 조정 | 같은 데이터로 두세 표현을 나란히 렌더해 시각 문법 결정 |
| 3 | 선택 API·신규 종류·패널 보완 | 선택된 표현에 필요한 API와 역할 토큰을 추출 |
| 4 | 소비 앱 전환 | 호환성·성능·접근성 검증 후 소비 앱 전환 |

현재 목적이 flex의 조형과 서비스 경험을 더 잘 반영하는 것이라면 B의 순서가 적합하다. 다만 공용 export 승격과 코드 변경 범위는 실제 소비자와 승인된 스펙으로 결정한다. 이번 작업은 비교 자료 작성이며 런타임 코드를 변경하지 않았다.
