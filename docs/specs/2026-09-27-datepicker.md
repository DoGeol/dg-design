## 목표

dg-design 소비 앱이 데스크톱과 모바일에서 단일 날짜, 날짜 범위, 날짜+시간, 날짜+시간 범위를 일관되게 입력하고 검증할 수 있는 `DatePicker`와 `DateRangePicker`를 제공한다.

## 공개 동작과 값 계약

- 공개 진입점은 `DatePicker`(단일)와 `DateRangePicker`(시작·종료)로 나누고 달력·시간 입력 모델과 시각 요소를 공유한다. 날짜 범위의 양 끝은 화면에서 포함해 표시한다. 종료일을 다음 날 자정으로 자동 변환하지 않는다.
- 각 진입점은 **날짜만**, **시간대 없는 날짜+시간**, **시간대 있는 날짜+시간**을 명시적으로 구분한다. 공개 타입은 서로 다른 종류의 값이나 시작·종료 값의 혼합을 거부한다. 날짜만의 값에 브라우저 시간대를 암묵적으로 붙이지 않는다.
- 시간대 있는 모드에서 앱이 IANA 시간대를 제공한다. DatePicker는 이를 표시하고 해당 시간대에서 날짜·시간을 해석하지만, 시간대를 바꾸는 컨트롤은 제공하지 않는다. 존재하지 않는 현지 시각(서머타임 전환 등)은 조용히 보정하지 않고 오류로 표시한다.
- 시간 입력은 분 단위다. 표시의 12/24시간제, 날짜 순서, 주 시작일은 locale에 맞춘다. 초 입력은 범위 밖이다.
- controlled와 uncontrolled 값을 모두 지원하고, 선택 없음은 `null`로 표현한다. 소비 앱은 변경 이벤트에서 확정된 값만 받는다. 폼 제출 시 단일 `name`, 범위의 시작·종료 `name`을 지정할 수 있어야 한다.

## 입력·확정 경험

- 달력 선택과 직접 입력을 모두 제공한다. 직접 입력 중의 미완성·잘못된 문자열은 편집 상태로 보존하고 확정 값으로 전달하지 않는다. 오류는 해당 입력 옆에 설명한다.
- **단일 날짜만** 달력에서 고르면 즉시 확정하고 패널을 닫아 트리거로 포커스를 되돌린다. 직접 입력은 유효한 값으로 완성한 뒤 Enter 또는 blur에서 확정한다.
- **범위 또는 시간이 포함된 모드**는 임시 선택을 보여주고 `적용`을 눌러 확정한다. `취소`, Escape, 바깥 닫기는 임시 선택을 버린다. 잘못된 값이 있으면 적용을 막고 이유를 표시한다.
- 데스크톱은 트리거에 붙는 팝오버를 사용한다. 범위 선택에는 두 달 보기를 제공하고, 화면이 좁으면 한 달로 줄인다. 모바일은 모든 모드에서 전용 시트를 사용하고 한 달 보기·현재 선택 요약을 제공한다. 적용·취소는 범위·시간 모드에만 두고, 단일 날짜는 모바일에서도 즉시 확정한다.
- 빠른 선택 프리셋은 선택 사항인 공개 입력으로 받는다. 앱이 레이블과 **현재 시각·시간대에서 계산한 완전한 값**을 제공하며, 컴포넌트는 이를 표시하고 모드별 확정 규칙에 따라 적용한다. 앱 고유의 프리셋 이름·계산식은 패키지에 내장하지 않는다. 제약을 위반하는 프리셋은 선택되지 않고 이유가 드러난다.

## 제약과 오류

- 최소·최대 날짜/시간, 선택 불가 날짜를 지정할 수 있다. 범위는 시작이 종료보다 늦을 수 없고, **중간에 선택 불가 날짜가 하나라도 있으면** 전체 선택을 막고 이유를 표시한다. 같은 날의 범위는 시간 순서가 유효하면 허용한다.
- 입력 불가, 빈 값, 허용 범위 초과, 잘못된 직접 입력, 존재하지 않는 시간, 유효하지 않은 프리셋의 오류를 구분한다. 앱이 사용자에게 보여줄 오류 문구를 재정의할 수 있다.
- 월·연도 경계, 윤년, 로케일별 날짜 순서, DST 전환일에서 범위 판정과 표시가 일치해야 한다.

## 접근성·화면 적응

- 단일 입력은 `Field`의 레이블·설명·오류 연결을 따른다. 범위의 두 입력은 그룹 레이블과 시작·종료 각각의 이름·ID·오류 연결을 갖는다. 달력에는 접근 가능한 이름과 날짜 그리드 키보드 탐색을 제공한다. 월 이동과 선택 변경을 보조 기술에 알리고, 닫을 때 트리거로 포커스를 되돌린다.
- 키보드만으로 직접 입력, 달력 탐색, 범위 양 끝 수정, 시간 수정, 프리셋 선택, 적용·취소를 마칠 수 있다. 포인터 드래그는 유일한 범위 선택 수단이 아니다.
- 모바일 날짜 셀과 주요 동작의 터치 영역은 44×44 CSS px 이상을 목표로 한다. 375px 폭, 확대, 가상 키보드, 세로 스크롤에서 시트의 선택 요약과 적용 동작이 가려지지 않는다.
- 화면 자동 검사는 접근 가능한 이름·상태·포커스를 확인하고, 릴리스 전 실제 모바일과 스크린리더 청취 검증을 별도로 수행한다.

## 하지 않을 것

- DatePicker 내부 시간대 선택기, OS 네이티브 날짜 선택기.
- 초 단위 입력, 반복 일정, 여러 개의 분리된 기간, 주·월 단위 전용 선택기.
- 서버에서 예약 가능 시간을 조회하거나 앱별 업무 시간·예약 정책을 판단하는 기능. 앱이 선택 제약과 프리셋 값을 제공한다.
- 음력 등 비그레고리력 선택 UI는 첫 버전에서 다루지 않는다.

## 합격 조건

- [ ] 두 공개 컴포넌트의 값 타입이 단일/범위 및 날짜/현지 날짜시간/시간대 포함 날짜시간을 구분하고, 잘못 섞은 입력은 typecheck에서 실패한다.
- [ ] 네 사용 방식이 데스크톱 팝오버와 모바일 시트에서 선택·직접 입력·값 지우기를 완료한다.
- [ ] 단일 날짜 달력 선택은 즉시 변경 이벤트를 내고, 범위·시간 모드는 적용 전까지 변경 이벤트를 내지 않는다. 취소·Escape는 기존 값을 보존한다.
- [ ] 소비 앱이 제공한 프리셋은 유효할 때만 선택 가능하고, 날짜·시간·시간대 값을 손실 없이 적용한다.
- [ ] 최소·최대, 시작/종료 순서, 중간 선택 불가 날짜, 같은 날 시간 순서, 잘못된 직접 입력, 윤년·월 경계·DST가 검증된다.
- [ ] 키보드만으로 모든 흐름을 마칠 수 있고, 범위의 두 입력 이름·오류, 모바일 터치·포커스 복귀가 브라우저 검사에서 확인된다.
- [ ] Storybook에 네 사용 방식 및 오류·비활성·프리셋 상태가 있고, 기존 패키지 CI(generate/build/test/typecheck/publint/VR)가 통과한다. VR에 375px 모바일 검사·Linux 시각 기준을 추가하고 실제 스크린리더 청취를 릴리스 전 완료한다.

## 드러난 가정과 결론

| 가정 | 어떻게 흔들었나 | 결론 |
| --- | --- | --- |
| 시간대가 있는 시각만 지원하면 범용적일 것이다 | 현지 시각과 실제 시점을 구분해 선택 | 둘 다 지원하되 소비 앱이 값 종류를 명시한다 |
| 프리셋을 컴포넌트에 내장하면 편리하다 | 상대 기간의 기준과 시간대가 앱마다 다름을 확인 | 앱이 계산하고 DatePicker가 표시한다 |
| 모바일은 네이티브 날짜 입력이면 충분하다 | 단일 날짜만 네이티브로 바꾸는 선택지를 비교 | 모든 모드에서 전용 시트를 사용한다 |
| 선택 불가 날짜를 지나는 범위도 허용할 수 있다 | 중간에 막힌 날짜가 있는 예시로 확인 | 첫 버전은 범위 전체를 막고 이유를 표시한다 |

## 기술 맥락

- dg-design은 `packages/react`에 컴포넌트별 폴더·서브패스 export·Storybook·Vitest·Playwright VR을 둔다.
- [컴포넌트 구성 규칙](../decisions/2026-09-05-component-composition-rules.md)은 공유 상태·aria 연결이 있는 요소를 compound로 만든다. 날짜 입력은 기존 `Field`, 데스크톱의 `Popover`, 모바일의 `Sheet`와 연결된다.
- 현재 날짜 전용 컴포넌트·날짜 계산 라이브러리는 없다. 구현 계획에서 날짜 연산 라이브러리와 공개 값 타입을 정하되, 위 세 값 의미와 타입 안전성은 유지한다.

## 남은 위험

- 공개 값 표현과 날짜 연산 라이브러리 선택은 패키지 사용법·번들 크기에 영향을 준다. 구현 계획에서 소비 앱 예제와 함께 확정한다.
- 기존 `Field`는 입력 ID 하나만 관리하고, `Popover.Content`의 기본 role은 `group`이다. 범위의 두 입력 이름과 달력 포커스는 별도 배선이 필요하다.
- 기존 `Sheet`의 bottom 레이아웃은 작다. 달력·시간·프리셋의 높이와 가상 키보드를 함께 검증해야 한다. 팝오버↔시트 전환 시 열린 상태·임시 값·포커스도 보존해야 한다.
- 서머타임의 중복 시각, 모바일 가상 키보드, 실제 보조 기술의 날짜 그리드 발화는 자동 테스트만으로 충분히 확인되지 않는다.
