# DDS 토큰 체계와 Button 0.1.0 — 인터뷰 기록

<details><summary>전체 Q&A (11라운드)</summary>

### Round 0 — 토폴로지
**Q:** 구성요소 6개 + 보류 3개(CI, 컴포넌트 테스트, 시각 회귀)가 맞나?
**A:** "나중에 구현해도 문제 없을까?" → 나중 도입 비용이 일정한지 누적되는지로 분석. 시각 회귀만 누적이나 baseline이 필요한 시점이 아직 아님. CI는 공개 저장소라 무료임을 확인하고 **진행으로 승격**

### Round 1 — 컬러 팔레트 구조
**Q:** primitive 색 스케일을 어떻게 만들까? (OKLCH 파생 / 오픈 팔레트 차용 / 수작업)
**A:** "seed는 어떻게 구현하고 있는지 확인" → 조사 결과 손으로 고른 hex + **모드 다이얼 2개** 발견. 선택지를 다이얼 위치 결정으로 재구성 → **semantic에서만 분기**
**모호도:** 100% → 73%

### Round 2 — 비색상 토큰 레이어
**Q:** 치수·radius·타이포를 어떤 레이어 구조로? seed는 semantic 치수 레이어가 없고 컴포넌트가 primitive를 직접 참조한다
**A:** A — primitive 수치 스케일만
**모호도:** 73% → 66%

### Round 3 — Button prop 구조
**Q:** variant를 합성 단일 prop(seed)으로 할까, intent × variant 2-prop으로 할까?
**A:** B — 2-prop
**모호도:** 66% → 66% (Storybook이 최저값을 붙잡음)

### Round 4 — 반론 챌린지
**Q:** Storybook이 정말 필요한가? 컴포넌트 1개고 소비 검증 앱과 중복될 수 있다
**A:** 유지 — 두 앱의 검증 대상이 다름(빌드 전 소스 vs 설치된 패키지)
**모호도:** 66% → 50%

### Round 5 — 공개 API 범위
**Q:** primitive 팔레트를 공개할까?
**A:** "공개해야 하는 건 뭐야" → 강제 공개분(경로·props·`data-dds-theme`·semantic) 정리 후 재질문 → **닫는다**
**모호도:** 50% → 46%

### Round 6 — 단순화 챌린지
**Q:** CSS 클래스를 공개 API로 선언할까? 가장 단순한 답은 "약속하지 않는 것"이나 specificity 문제가 남는다
**A:** 비공개 + 전체를 `@layer dds`에
**모호도:** 46% → 46%

### Round 7 — 대비 검사 쌍 선언
**Q:** 명시 배열 / 규칙 생성 / 전수 검사?
**A:** "seed는 어떻게 구현되어 있어?" → **seed에 대비 검사 코드가 전무함**을 확인. DDS 고유 결정으로 재분류 → A 명시 배열
**모호도:** 46% → 43%

### Round 8 — 램프 스텝 체계
**Q:** 10단계 seed 번호 체계 / 12단계 Radix / 필요분 5~6단계?
**A:** A — 10단계 100~1000. hover/pressed 한 스텝 이동을 표현하려면 램프가 촘촘해야 함
**모호도:** 43% → 36%

### Round 9 — disabled 구현
**Q:** native `disabled` / `aria-disabled` / 둘 다?
**A:** A — native. 3중 셀렉터가 전환 문을 열어둠
**모호도:** 36% → 36%

### Round 10 — 타이포 구조
**Q:** 인덱스 공유 2스케일(seed) / 묶음 토큰 / raw px?
**A:** A — 인덱스 공유. 10라운드 체크포인트에서 "hue 한 라운드 더" 선택
**모호도:** 36% → 29.5%

### Round 11 — brand hue
**Q:** 보라 290 / 파랑 255 / 주황 45 / 청록 195? 대비 검사를 강제하므로 hue가 solid 스텝 폭을 좌우한다
**A:** 청록 195
**모호도:** 29.5% → 18% (임계값 통과)
